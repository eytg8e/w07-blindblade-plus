# PLAN_0005 — 게임 씬 공통 구조 및 입력 관리

## 목표

게임 씬에는 공통 기능의 진입점인 GameSceneInitializer와 Player 프리팹을 배치하고, 공통 매니저 구성과 초기화는 한곳에서 관리한다. 현재 플레이어 참조는 Game.Player로 제공하며, 라운드 로직이 입력 어댑터와 UI를 직접 제어하지 않도록 입력 허용·게임 상태·UI 표현 책임을 분리한다.

## 구현 단위

1. 현재 플레이어 참조와 수명 정리
   - Game에 현재 PlayerController를 반환하는 읽기 전용 Game.Player 접근점과 등록·해제 경로를 마련한다.
   - 씬 종료 시 해당 플레이어의 등록과 이벤트 연결을 해제하고, 다음 씬의 플레이어로 교체한다. 플레이어를 자동 생성하거나 DontDestroyOnLoad로 유지하지 않는다.
   - 현재 플레이어를 참조해야 하는 외부 클래스만 Game.Player 기준으로 연결한다. 플레이어 내부 컴포넌트와 특정 캐릭터를 참조하는 코드는 기존 직접 참조를 유지한다.
2. 입력 허용 책임을 Game 하위 InputManager로 이동
   - PlayerInputCommandAdapter는 바인딩과 플레이어 명령 변환을 유지하고, InputManager가 게임플레이 입력 허용 여부를 관리한다.
   - 기존 InputManager.cs의 실제 클래스인 PlayerInputController의 사용처와 책임을 확인한다. 기존 기능을 임의로 삭제·통합하지 않으며, 이름 및 공용 입력 책임이 겹치면 구현 전에 정리 방안을 확정한다.
   - 기존 PlayerInputCommandAdapter와 KatanaInputCommandAdapter 모두 동일한 입력 허용 정책을 적용한다. 게임플레이 입력을 차단해도 UI 입력은 유지한다.
   - 입력 차단 시 남은 이동·시점 입력과 가드·차지 유지 상태를 정리하고, 재시작 및 입력 재허용 시 눌림 상태를 일관되게 처리한다.
   - 어댑터 비활성화에 따른 커서 변경이나 Action 취소 콜백에 의존하지 않도록 명시적인 입력 제어 경로를 마련한다.
3. 게임 상태와 게임오버 UI 책임 분리
   - GameStateManager가 초기화 중·플레이 중·게임오버·재시작 중의 필요한 상태와 중복 전환 방지를 관리하고 상태 변경 이벤트를 제공한다.
   - InputManager는 상태 변경을 받아 플레이어 입력 허용 여부를 적용한다. 입력 정책의 소유자는 InputManager로 한정한다.
   - UIManager는 상태 변경을 받아 기존 게임오버 패널 표시, 버튼 선택 및 버튼 요청 전달을 담당한다. 새로운 화면이나 디자인은 추가하지 않는다.
   - CorridorRoundController는 첫 적중 여부와 피해에 따른 기존 패배 조건을 유지하고 GameStateManager에 게임오버를 요청한다. 입력 어댑터 비활성화와 패널 직접 활성화 책임을 제거한다.
   - 기존 플레이어 사망 처리, 사운드 정리, 시간 정지·복구, 커서 전환, 현재 씬 재시작과 머무르기 동작의 담당을 명확히 이관한다. 상태 이벤트 재진입과 씬 종료 시 복구를 처리한다.
4. 플레이어 전투 서비스 배치 통일
   - 현재 플레이어 공격 판정과 대상 조회를 담당하는 EnemyCombatService를 Player 프리팹 내부로 이동한다. 클래스명과 IPlayerCombatService 계약 및 피해 규칙은 유지한다.
   - ConfigurePlayer, PlayerController.ConfigureCombatService와 PlayerCombatEffects의 접촉 이벤트 참조를 플레이어 구성 안에서 연결한다.
   - 씬 루트의 서비스 검색과 중복 배치를 제거하되, 기존 적 Target 연결과 같은 씬 대상 제한을 보존한다.
5. GameSceneInitializer에서 공통 구성과 초기화 순서 제어
   - 공통 매니저 프리팹과 씬별 설정을 인스펙터로 연결한다. 맵별 지형 기억 범위·해상도·반경 및 선택적인 기능 차이는 씬 설정으로 유지한다.
   - 기존 Game의 SensoryManager·EffectManager 생성 경로를 존중하고, 같은 서비스를 다시 생성하지 않는다. Game의 영속 서비스와 씬별 세션·UI·TerrainMemory의 수명을 구분한다.
   - 입력 차단 상태에서 공통 서비스 확보 → Game.Player 등록 → 플레이어 전투·입력·상태·UI 참조 연결 → MainMapSession 및 TerrainMemory 초기화 → 플레이 상태 전환 순으로 준비한다.
   - MainMapSession의 초기화와 런타임 발소리 처리를 구분하고, 전투 서비스 씬 검색은 플레이어 내부 연결로 대체한다.
   - TerrainMemory의 텍스처 생성·셰이더 등록·관측자 연결 시점을 명시적으로 제어하며, 씬 종료 시 기억과 셰이더 상태를 정리한다.
   - 관련 Awake·OnEnable·Start의 기존 자동 실행을 확인해 명시적 초기화와 중복되지 않도록 조정한다. 전체 프로젝트의 Lifecycle을 일괄 변경하지 않는다.
6. 실제 게임 씬 적용 및 기존 동작 검증
   - 각 씬과 Player.prefab의 구성 차이·추가 컴포넌트·Override를 확인하고, 공통 구성만 원본으로 통일한다. 위치·맵별 난이도·기믹 설정은 유지한다.
   - StraightCorridor, TCorridor, Stairwell, MainMap의 적용 여부와 씬별 차이를 확인한다. KatanaCombatPreview와 PlayerDebugSandbox는 기존 검증 기능을 유지하며 필요한 호환 연결만 검토한다.
   - 게임 씬의 공통 기능은 Initializer와 Player 중심으로 배치하되, 지형·적·문·라운드 규칙 등 맵 고유 객체는 유지한다.
   - 기존 검증 수단으로 씬 단독 실행, 입력·전투·감각·지형 기억, 게임오버 UI 조작, 재시작과 씬 이동을 확인한다. 테스트 코드와 임시 검증 스크립트는 작성하지 않는다.
   - 구현 Task별 관련 기능명세와 실제 검증 결과를 갱신한다. 실행하지 않은 검증은 미확인으로 기록한다.

7. 공통 구조 변경의 수동 검증 씬 제공
   - 생산용 플레이어와 Initializer를 사용하는 GameArchitectureValidation 씬을 추가한다.
   - 기존 API에 연결한 테스트 서비스 Variant의 버튼과 근접 적·지형 기억으로 변경 의도를 재현한다.
   - 새 테스트 코드 없이 사용 안내와 실제 검증 결과를 기록한다.

## 완료 조건

- 현재 플레이어가 필요한 외부 기능이 Game.Player를 사용하고, 씬 전환 후 이전 플레이어 참조와 이벤트 구독이 남지 않는다.
- CorridorRoundController가 입력 어댑터·게임오버 패널을 직접 제어하지 않으며, 기존 첫 적중 전 피격 및 사망에 따른 패배 조건은 유지된다.
- InputManager가 두 플레이어 입력 어댑터의 입력 허용을 관리하고, 게임오버 중 UI 조작은 가능하며 이동·가드·차지 입력이 남지 않는다.
- 게임오버 상태 전환과 UI 표시가 각각 GameStateManager와 UIManager에서 수행되고, 중복 사망 알림에도 한 번만 전환된다.
- EnemyCombatService가 플레이어 내부에서 기존 전투·이펙트 계약을 제공하며 씬 루트 서비스를 요구하지 않는다.
- GameSceneInitializer가 공통 구성과 의존성 초기화 순서를 제어하고, 영속 매니저의 중복 생성 및 이전 씬 상태 유출이 없다.
- 적용한 게임 씬에서 플레이어 공통 기능 수정은 원본 프리팹 및 공통 구성에 반영하는 것으로 충분하며, 맵별 참조·배치·설정은 보존된다.
- 기존 이동·공격·가드·발도·피격·감각·지형 기억·게임오버·재시작 동작의 검증 결과와 한계가 관련 명세에 기록된다.
- 이 문서는 구현 계획이다. 코드·씬·프리팹 수정은 구현 모드와 첫 Task를 확정한 뒤 진행하며, 현재 항목을 구현 완료로 간주하지 않는다.
